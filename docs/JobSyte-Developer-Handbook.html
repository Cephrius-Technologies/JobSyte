Purpose. This document is the developer guide for the current JobSyte web application. It explains the product scope, the runtime architecture, the route and module map, the data boundaries, and the exact files a developer should change when adding features, refactoring, or fixing defects.

1. Product Scope

JobSyte is a contractor operations platform built on Next.js App Router and Supabase. The product covers multi-company project management, job scheduling, invoice generation, accounting expense tracking, employee and crew management, payroll/payment tracking, reporting, global search, settings/preferences, and release-note visibility.

The current workspace does not contain the older employee-app/ tree referenced by some historical docs. This handbook reflects the files that exist in the current repository only.

5. Runtime Architecture

5.1 Root shell

app/layout.tsx is the global shell. It loads fonts, global CSS, theme support, toaster support, and document title synchronization. It is the first file to read when understanding how the app boots.

5.2 Authenticated shell

app/(jobsyte-app)/layout.tsx is the authenticated product gate. It verifies the Supabase session, loads the companies the user belongs to, and mounts CompanyProvider so the rest of the app can read the active company.

5.3 Tenant scoping

Multi-company scoping is enforced through two files:

  • lib/company-context.ts stores the selected company in local storage and the jobsyte:active-company-id cookie.
  • lib/active-company.ts reads that cookie inside server components and server actions.

Any new data query or mutation that touches business data should use getActiveCompanyId() instead of trusting company IDs passed from the browser.

5.4 Supabase clients

  • lib/supabase/server.ts: normal authenticated SSR and server-action access
  • lib/supabase/client.ts: browser-side client access when needed
  • lib/supabase/admin.ts: service-role access for cron and privileged cleanup
  • proxy.ts: session refresh middleware

5.5 Page composition pattern

Most features follow the same shape:

  1. A server page in app/(jobsyte-app)/... loads company-scoped data.
  2. The page passes typed rows into a client component under components/<feature>/.
  3. Dialogs, menus, and tables in that client component call server actions in the same route group.
  4. The server action writes to Supabase, revalidates affected paths, and returns a small result object.

8. Data Model Surface Visible In Code

The following tables are directly referenced by the current application code and therefore define the practical scope of the product:

  • company_members

  • jobs
  • builders

  • project_preset_jobs
  • invoices
  • invoice_items
  • employees
  • crews
  • payments

Several flows also depend on soft-delete columns such as deleted_at, and financial amounts are commonly stored as integer cents in fields such as price_cents, subtotal_cents, and amount_cents.

Migrations and SQL assets

  • supabase/migration_employee_login.sql
  • supabase/migration_employee_profile.sql
  • supabase/migration_project_presets.sql
  • scripts/add-payment-tracking.sql

When changing schema-sensitive behavior, read the relevant SQL file before changing the application code. The app code frequently encodes assumptions about nullable columns, soft deletes, and enum-like string values.

9. How To Add Features

  1. Choose the route group first. Identify whether the feature belongs under projects, invoices, calendar, accounting, settings, or another existing vertical.
  2. Add or extend the server page query. Page-level data loading lives in the route file under app/(jobsyte-app)/....
  3. Keep interactivity in a client component. The interactive workbench almost always belongs under components/<feature>/.
  4. Add mutations in server actions. Create or extend the nearest actions.ts file inside the route group instead of posting directly from the client to Supabase.
  5. Use company scoping. New reads or writes that touch business data should call getActiveCompanyId().
  6. Update shared types near the feature. Examples include components/projects/types.ts and components/accounting/types.ts.
  7. Revalidate affected routes after mutations using revalidatePath().
  8. Update surrounding UX when necessary. This may include sidebar navigation, document title sync, search indexing, breadcrumbs, filter dialogs, release notes, and empty states.
  9. Add or extend tests when the change affects parsing, derived data, or shared utilities.
  10. Run at least npm run lint. For logic-heavy changes, also run npm run test:run and npm run build.

10. How To Refactor Safely

  1. Trace the full vertical slice before changing anything: page route, client component, server action, helper library, tests.
  2. Do not move company-scoping logic into the client. Keep tenant guards on the server.
  3. Preserve the existing page pattern: server page loads data, client component owns interaction, server action owns mutation.
  4. When extracting shared UI, prefer the feature folder first. Promote to components/ui/ only when the abstraction is truly general.
  5. When refactoring data shapes, update all dependent types and derived views together. Search categories, grouped project views, and calendar job cards are all shape-sensitive.
  6. Keep financial values in cents and keep date-only values in YYYY-MM-DD format where existing code expects it.
  7. Run lint and relevant tests before considering the refactor done.

11. How To Fix Bugs

  1. Reproduce the bug in the page route first.
  2. Identify whether the failure is in the page query, client state, server action, or shared helper.
  3. Check company scoping and auth. Many bugs in Supabase apps come from missing tenant guards.
  4. Check date handling. The app uses both date-only fields and timestamp fields, especially in jobs, invoices, and cron logic.
  5. Check soft-delete filters. Several list queries intentionally exclude rows where deleted_at is not null.
  6. Add a regression test when the bug lives in a helper, formatter, parser, or reusable component.
  7. Run npm run lint at minimum before closing the fix.

Verification workflow

  1. Run npm run lint for every change.
  2. Run npm run test:run when changing shared utilities, parsers, notifications, preference logic, or reusable components.
  3. Run npm run build when refactoring route boundaries, shared types, or server components.
  4. Do a manual pass on the affected route and at least one small-screen viewport for UI work.

14. Development Conventions

  • Prefer server components for data loading and client components for interactivity.
  • Prefer colocated feature files under components/<feature>/ instead of creating new broad shared layers.
  • Keep mutation logic in server actions, not in browser-only Supabase calls.
  • Use existing UI primitives from components/ui/ before inventing new controls.
  • Preserve the current design language. This codebase already has an established shell, cards, filters, dialogs, and table patterns.
  • Update release notes when a change is user-facing and intended for a shipped version.
  • When a feature introduces a new entity or workflow, add the search integration if users would reasonably expect to find it globally.

16. Recommended Onboarding Path For A New Developer

  1. Read README.md for the high-level product summary.
  2. Read app/layout.tsx and app/(jobsyte-app)/layout.tsx to understand the shell split.
  3. Read lib/company-context.ts and lib/active-company.ts to understand tenant scoping.
  4. Read one full vertical such as projects: app/(jobsyte-app)/projects/page.tsx, components/projects/projects-page.tsx, app/(jobsyte-app)/projects/actions.ts.
  5. Read one finance vertical such as invoices: app/(jobsyte-app)/invoices/page.tsx, components/invoices/create-invoice-dialog.tsx, app/(jobsyte-app)/invoices/actions.ts.
  6. Read app/api/cron/preferences/route.ts and lib/notifications/templates.ts if your work touches notifications or preferences.
